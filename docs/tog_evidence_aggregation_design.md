# ToG Evidence Aggregation Design Note

This note is Phase 0 for the new direction: use the official ToG repository as the base system and inspect its generated paths/candidate answers before implementing any new scorer.

Official base repo cloned at:

```text
external/ToG
```

The main source files are:

```text
external/ToG/ToG/main_freebase.py
external/ToG/ToG/utils.py
external/ToG/ToG/freebase_func.py
external/ToG/ToG/main_wiki.py
external/ToG/ToG/wiki_func.py
external/ToG/ToG/prompt_list.py
```

## Current ToG Flow

The easiest path to inspect first is the Freebase runner:

```text
external/ToG/ToG/main_freebase.py
```

At a high level, ToG does:

1. Load a dataset item and its topic entity.
2. For each search depth:
   - collect local relations around the current topic entities,
   - ask a scorer/pruner to select useful relations,
   - execute those relations to get candidate next entities,
   - score/prune candidate entities,
   - keep the top entities as the next beam/frontier,
   - ask the LLM whether the gathered triples are sufficient to answer.
3. If sufficient, save the LLM answer and reasoning chains.
4. If search fails or reaches the end, generate an answer directly or from partial paths.

This is not a clean “generate all candidate paths, then rank final answers” architecture. The official code interleaves path generation, pruning, and answer sufficiency checks.

## Where Candidate Paths Are Generated

Candidate paths are built in `main_freebase.py` inside the depth loop.

The relation expansion call is:

```python
retrieve_relations_with_scores = relation_search_prune(...)
```

That function lives in:

```text
external/ToG/ToG/utils.py
```

It returns relation candidates like:

```python
{
  "entity": entity_id,
  "relation": relation_name,
  "score": relation_score,
  "head": True or False
}
```

Then `main_freebase.py` executes each selected relation using:

```python
entity_search(entity["entity"], entity["relation"], entity["head"])
```

This returns candidate next entity IDs.

Each candidate entity is then scored by:

```python
entity_score(question, entity_candidates_id, entity["score"], entity["relation"], args)
```

The path-level information is collected through:

```python
update_history(...)
```

The relevant arrays are:

```text
total_entities_id
total_relations
total_candidates
total_topic_entities
total_head
total_scores
```

Together, one candidate path edge is:

```text
topic_entity --relation--> candidate_entity
```

with score:

```text
entity_score * relation_score
```

## Where Beam Search Happens

Beam pruning happens in:

```python
entity_prune(...)
```

in `external/ToG/ToG/utils.py`.

The code sorts candidate entity expansions by `total_scores`:

```python
zipped = list(zip(total_entities_id, total_relations, total_candidates, total_topic_entities, total_head, total_scores))
sorted_zipped = sorted(zipped, key=lambda x: x[5], reverse=True)
```

Then it keeps only the top `args.width`:

```python
entities_id, relations, candidates, topics, heads, scores = ...[:args.width]
```

So ToG's beam is an entity/path beam. It does not keep a full explicit tree object, but the beam state can be reconstructed from:

```text
entities_id
relations
candidates
topics
heads
scores
cluster_chain_of_entities
```

## Where Candidate Answers Are Produced

There are two answer notions in ToG:

1. Candidate entities reached by graph search.
2. The final answer string generated by the LLM from retrieved triples.

The graph candidate entities are produced before `entity_prune(...)`, specifically from:

```text
total_candidates
total_entities_id
total_scores
```

The final answer is produced by:

```python
reasoning(question, cluster_chain_of_entities, args)
```

in `utils.py`.

`reasoning(...)` builds a prompt containing the retrieved triples:

```text
Knowledge Triplets: ...
```

and asks the LLM whether the evidence is sufficient. If the LLM says yes, ToG saves that answer.

Therefore, for our evidence aggregation work, the candidate answer pool should initially be defined as:

```text
all candidate entities reached by ToG before entity_prune, plus the retained beam entities after entity_prune
```

The final ToG answer is a separate generated string and should be treated as ToG's original output, not as the full candidate pool.

## Where Final Answer Ranking/Scoring Happens

ToG does not have a separate final answer reranker in the usual sense.

Its baseline ranking comes from:

1. relation score from `relation_search_prune(...)`,
2. entity score from `entity_score(...)`,
3. multiplication/propagation into `total_scores`,
4. sorting in `entity_prune(...)`.

The answer string is then generated by the LLM from the retained triples.

So the closest baseline score/rank for candidate answers is:

```text
entity_prune rank based on total_scores
```

This matters for our future experiment: the cleanest comparison is not “replace ToG's LLM answer generator” first. It is:

```text
keep ToG path generation fixed
collect all candidate answer entities and supporting paths
compare ToG's total_scores-based rank against a new answer aggregation score
```

## What Counts as a Candidate Answer

For Phase 1 tracing, candidate answers should be recorded at two levels:

### Pre-prune candidates

These are all `(candidate entity, relation, source entity, score)` expansions produced during a depth step before beam pruning.

They are useful for measuring whether ToG generated the gold answer but pruned it away.

### Retained beam candidates

These are the top `args.width` entities kept by `entity_prune(...)`.

They are useful for measuring what ToG actually lets the LLM reason over.

For the first evidence aggregation experiment, we should probably score over pre-prune candidates within the same generated frontier, then compare against ToG's retained ranking. That preserves path generation while testing final answer scoring.

## What Counts as a Supporting Path

A supporting path is a sequence of ToG graph expansions that reaches a candidate answer.

At minimum, ToG exposes one-hop edges:

```text
source entity --relation--> candidate entity
```

Across depths, `cluster_chain_of_entities` stores selected triples:

```python
[(topic_name, relation, candidate_name), ...]
```

However, the official code does not preserve explicit parent pointers from depth to depth. That means full multi-hop path reconstruction may be approximate unless we add tracing at each expansion step.

For Phase 1, we should record:

```text
depth
source entity ID/name
relation
direction/head flag
candidate entity ID/name
score
whether candidate was retained by entity_prune
```

Then we can reconstruct approximate paths by linking retained entities across depths.

## Path-Level Information Available

Available directly:

```text
question text
topic entity ID/name
depth
relation name
head/tail direction flag
candidate entity ID
candidate entity name
relation score
entity score / total score
whether retained after pruning
cluster_chain_of_entities
```

Not cleanly available without instrumentation:

```text
full parent pointer for each candidate
all alternative paths to the same answer across depths
LLM confidence for final generated answer
explicit final answer candidate distribution
```

## Answer-Level Information Available

Available:

```text
dataset gold answer
ToG generated final answer string
candidate entity names
candidate entity IDs
score/rank from total_scores
reasoning chains saved by ToG
```

Need to add:

```text
candidate answer grouping by normalized answer string/entity ID
all supporting paths per candidate answer
best path score per candidate answer
number of paths per answer
path diversity summary
whether gold answer appears in candidate pool
whether gold answer appears in retained beam
```

## Where the New Scorer Would Plug In Later

The future scorer should plug in after ToG has generated candidate expansions and before changing any search behavior.

The safest first plug-in point is after `entity_prune(...)` diagnostics are collected:

```text
ToG generates relation/entity candidates exactly as before
ToG computes original scores exactly as before
we group candidate entities into answer candidates
we compute a new score from their supporting paths
we compare new ranking vs ToG ranking offline
```

This avoids changing:

```text
relation pruning
entity expansion
beam width
entity linking
LLM prompts
KG backend
```

Only after that offline comparison is meaningful should we consider using the new scorer inside the live ToG loop.

## Keeping Candidate Path Generation Fixed

The experimental rule should be:

```text
One ToG run produces a frozen candidate path pool.
All scoring methods read the same frozen pool.
No scorer is allowed to request more KG edges, change prompts, change beam search, or add candidates.
```

The frozen pool should be saved as:

```text
runs/tog_evidence_probe/candidate_paths.jsonl
```

Each line should contain one question and all generated candidates/paths.

## Implementation Blockers and Risks

1. The official Freebase code has minor bugs in the cloned version.

   I observed:

   ```text
   pre head
   ```

   in `utils.py`, which is a syntax error, and an undefined retry flag in `run_llm`.

   These should be patched only as compatibility fixes before running.

2. ToG does not preserve full parent pointers.

   We can trace per-depth expansions, but exact multi-hop path grouping may require adding a parent/path ID during expansion.

3. ToG's final answer is generated by an LLM, not selected from an explicit candidate answer table.

   Therefore our first scorer comparison should be offline over candidate entities, not directly replacing the final answer prompt.

4. Gold answer matching is dataset-specific.

   WebQSP, CWQ, and SimpleQA store answers differently. The tracer needs dataset-specific answer extraction.

5. Candidate answer recall may be low.

   If ToG does not generate the gold answer often, answer reranking will not help much. That is exactly what Phase 1 is meant to measure.

6. Multiple-path support may be sparse.

   If most answers have only one path, an interaction-aware scorer will have little room to help.

## Stop Point

At this stage, no scorer should be implemented.

Next step after approval:

```text
instrument ToG to write candidate_paths.jsonl, metrics.json, report.md, and behavior_report.html
```

The tracing should keep ToG's candidate generation fixed and should not alter relation pruning, entity pruning, prompts, beam width, KG setup, or final answer generation.
